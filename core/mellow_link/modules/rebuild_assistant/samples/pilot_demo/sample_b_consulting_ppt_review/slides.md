# 업무 접수/처리 프로세스 개선 검토

## 1. 표지

### 제목

업무 접수/처리 프로세스 개선 검토

### 핵심 메시지

분산된 요청 접수와 처리 현황 관리를 표준 상태 체계와 통합 관리 흐름으로 정리한다.

### 본문 bullet

- 대상 업무: 부서 공통 요청 접수, 검토, 처리, 완료 관리
- 검토 범위: 접수 채널, 상태 기준, 처리 이력, 운영 현황 보고
- 산출 방향: 문제 진단, 개선 선택지, 권장안, 단계별 추진 계획

## 2. 배경 및 목적

### 제목

배경 및 목적

### 핵심 메시지

요청 채널이 여러 도구에 흩어져 처리 기준과 진행 상황을 한눈에 확인하기 어렵다.

### 본문 bullet

- 요청은 메일, 엑셀, 게시판, 메신저로 동시에 접수된다.
- 동일 유형 요청도 부서별 양식과 처리 기준이 다르다.
- 운영 현황 보고를 위해 담당자가 매주 수작업으로 자료를 취합한다.
- 개선 목적은 접수 채널 통합, 상태 기준 표준화, 처리 이력 관리, 현황 대시보드화다.

## 3. 현재 업무/시스템 현황

### 제목

현재 업무/시스템 현황

### 핵심 메시지

현재 흐름은 접수, 담당자 배정, 처리, 완료 확인이 도구별로 나뉘어 있다.

### 본문 bullet

- 메일 접수 건은 담당자가 개인 폴더와 엑셀 목록으로 관리한다.
- 게시판 접수 건은 댓글과 첨부 파일로 처리 결과를 남긴다.
- 긴급 요청은 메신저로 먼저 처리되고 나중에 목록에 추가된다.
- 부서장 보고용 현황은 별도 엑셀로 재작성된다.
- 처리 지연 사유와 담당자 변경 내역은 일관된 위치에 남지 않는다.

## 4. 주요 문제

### 제목

주요 문제

### 핵심 메시지

상태 기준, 책임 경계, 이력 관리가 약해 처리 누락과 지연 원인 파악이 반복된다.

### 본문 bullet

- 접수, 검토, 처리 중, 완료, 반려 상태의 정의가 부서마다 다르다.
- 요청 우선순위와 처리 기한이 명확히 기록되지 않는다.
- 담당자 변경 시 이전 판단과 지연 사유가 전달되지 않는다.
- 완료 처리 후 사용자 확인 절차가 없거나 비공식적으로 진행된다.
- 보고 자료 작성 시간이 실제 개선 활동 시간을 잠식한다.

## 5. 사용자/운영 관점 이슈

### 제목

사용자/운영 관점 이슈

### 핵심 메시지

요청자는 진행 상황을 알기 어렵고 운영자는 예외 처리와 문의 대응에 시간을 많이 쓴다.

### 본문 bullet

- 요청자는 자신의 요청이 접수되었는지, 누가 처리 중인지 확인하기 어렵다.
- 운영자는 동일 요청 여부를 매번 수동으로 확인한다.
- 긴급 요청과 일반 요청의 처리 우선순위가 명확히 구분되지 않는다.
- 반려 사유가 표준화되어 있지 않아 재요청 품질이 개선되지 않는다.
- 운영 리더는 지연 건의 원인을 현황표만으로 판단하기 어렵다.

## 6. 데이터/연계 관점 이슈

### 제목

데이터/연계 관점 이슈

### 핵심 메시지

요청 데이터 구조와 연계 기준이 약해 처리 현황을 자동으로 모으기 어렵다.

### 본문 bullet

- 요청 유형, 우선순위, 처리 기한, 담당 부서가 필수값으로 관리되지 않는다.
- 첨부 파일과 댓글 이력이 도구별로 분산되어 검색성이 낮다.
- 사용자 조직 정보와 담당자 정보가 최신 기준으로 연결되지 않는다.
- 기존 게시판, 메일함, 업무 포털 사이의 연계 범위가 정리되어 있지 않다.
- 대시보드에 사용할 기준일, 상태일, 완료일 정의가 명확하지 않다.

## 7. 개선 방향

### 제목

개선 방향

### 핵심 메시지

먼저 상태와 데이터 기준을 표준화하고, 이후 통합 접수/처리 흐름으로 확장한다.

### 본문 bullet

- 요청 유형과 필수 입력 항목을 표준화한다.
- 접수, 검토, 처리, 보류, 완료, 반려 상태 정의를 통일한다.
- 담당자 변경, 처리 의견, 지연 사유를 이력으로 남긴다.
- 반복 요청과 긴급 요청을 구분하는 처리 기준을 마련한다.
- 운영 현황은 별도 취합 없이 대시보드에서 확인하도록 한다.

## 8. 선택지 비교

### 제목

선택지 비교

### 핵심 메시지

단기 정리는 빠르지만 지속성은 낮고, 통합 포털 방식은 준비 범위가 크지만 운영 개선 효과가 높다.

### 본문 bullet

- A안: 기존 도구 유지 + 양식과 상태값만 정리
- B안: 접수/처리 표준 프로세스 수립 + 공통 관리 목록 운영
- C안: 통합 접수/처리 포털 구축 + 대시보드와 알림 연계
- 비교 기준: 적용 속도, 운영 부담, 이력 추적성, 보고 자동화 가능성
- 판단 포인트: 바로 실행할 표준화 작업과 중기 시스템 개선 작업을 분리해야 한다.

## 9. 권장안

### 제목

권장안

### 핵심 메시지

B안을 먼저 실행해 상태와 이력 기준을 고정한 뒤 C안을 단계적으로 추진한다.

### 본문 bullet

- 1단계에서는 요청 유형, 상태 정의, 필수 입력 항목을 확정한다.
- 공통 관리 목록으로 담당자, 기한, 지연 사유, 변경 이력을 구조화한다.
- 2단계에서는 접수 화면과 처리 화면을 통합하고 알림 기준을 적용한다.
- 3단계에서는 대시보드와 현황 보고 자동화를 연결한다.
- A안은 임시 안정화에는 사용할 수 있지만 장기 운영 기준으로는 한계가 있다.

## 10. 단계별 추진 계획

### 제목

단계별 추진 계획

### 핵심 메시지

업무 기준 정리, 데이터 정비, 통합 기능 설계, 파일럿 적용 순서로 추진한다.

### 본문 bullet

- 1주차: 요청 유형, 상태 코드, 처리 책임 기준 정리
- 2주차: 기존 목록 정비와 필수 항목 누락 현황 확인
- 3주차: 공통 관리 화면과 담당자 변경 이력 설계
- 4주차: 알림, 지연 기준, 완료 확인 절차 설계
- 5주차 이후: 대표 부서 파일럿 운영 후 전사 확산 여부 판단

## 11. 리스크 및 대응

### 제목

리스크 및 대응

### 핵심 메시지

부서별 운영 방식 차이를 무시하면 표준화가 형식화될 수 있으므로 단계별 합의가 필요하다.

### 본문 bullet

- 부서별 요청 유형이 달라 공통 기준 합의가 지연될 수 있다.
- 기존 도구를 즉시 중단하면 처리 누락이 발생할 수 있다.
- 과도한 입력 항목은 사용자 부담을 높일 수 있다.
- 담당자 변경 이력과 지연 사유 입력이 현장에 정착되지 않을 수 있다.
- 대응 방향은 필수 항목 최소화, 예외 유형 정의, 파일럿 운영 후 조정이다.

## 12. 기대 효과와 추가 검토 항목

### 제목

기대 효과와 추가 검토 항목

### 핵심 메시지

처리 흐름의 가시성과 책임 추적성이 높아지고 현황 보고 부담이 줄어든다.

### 본문 bullet

- 요청자는 접수 여부와 처리 상태를 직접 확인할 수 있다.
- 운영자는 담당자, 기한, 지연 사유를 기준으로 우선순위를 조정할 수 있다.
- 리더는 누락, 지연, 반복 요청을 대시보드에서 확인할 수 있다.
- 추가 검토 항목은 권한 범위, 알림 채널, 기존 게시판 자료 보존 기준이다.
- 최종 의사결정 전 대표 요청 유형 3~5개로 파일럿 검증이 필요하다.
