# 샘플 A: 레거시 주문관리 현대화 검토

## 샘플 목적

이 샘플은 오래된 주문관리 업무 시스템 자료를 업로드했을 때 MellowLink 판맥이 현행 구조, 핵심 문제, 개선 선택지, 리스크, 실행 준비 계획을 DOCX 보고서 초안으로 정리할 수 있는지 확인하기 위한 데모 입력 팩이다.

단일 SQL이나 코드 조각이 아니라 주문 조회, 결제 확인, 배송 상태 갱신, 관리자 수기 보정이 얽힌 작은 업무 덩어리로 구성되어 있다.

## 포함 파일 목록

- `business_overview.md`: 업무 목적, 사용자 역할, 주요 흐름, 현재 문제, 현대화 검토 목적
- `schema.sql`: 주문관리 관련 테이블 5개와 관계 설명
- `sql/01_order_search.sql`: 주문 조건 검색 SQL
- `sql/02_order_summary.sql`: 주문/결제/배송 집계 SQL
- `sql/03_order_status_update.sql`: 주문 상태 갱신 SQL
- `sql/04_payment_check.sql`: 결제 확인 및 불일치 점검 SQL
- `sql/05_delivery_pending.sql`: 배송 대기/지연 조회 SQL
- `code/OrderController.java`: 화면 요청을 받는 컨트롤러 흐름
- `code/OrderService.java`: 주문 상태 판단과 수기 보정이 섞인 서비스 흐름
- `code/OrderRepository.java`: SQL 파일과 연결되는 DAO 흐름
- `expected_report_outline.md`: 분석 결과와 비교할 기대 보고서 개요

## 검증하려는 기능

- 업무 설명, 테이블, SQL, 코드 흐름을 함께 읽어 하나의 현행 업무 구조로 묶는지 확인한다.
- 화면/서비스/DAO/SQL/테이블 간 결합도를 판단하는지 확인한다.
- 상태 변경 기준 불명확, 이력 부족, 수기 보정 의존, SQL 중복을 핵심 문제로 추출하는지 확인한다.
- 단순 코드 수정안이 아니라 단계적 현대화 선택지를 제시하는지 확인한다.

## 기대되는 DOCX 보고서 특징

- 첫 부분에서 "현행은 주문 상태 판단과 DB 갱신이 서비스/SQL에 분산되어 있다"는 결론이 드러나야 한다.
- 개선 선택지는 현행 유지, 서비스 계층 정리와 상태 이력 도입, 주문 상태 API와 이벤트/배치 재설계로 비교되어야 한다.
- 권장안은 B안 선행 후 C안 단계 추진으로 정리되는 것이 바람직하다.
- 리스크는 주문/결제/배송 상태 불일치, 수기 보정 누락, 일괄 전환 시 업무 중단 가능성을 포함해야 한다.
- 실행 준비 계획은 테이블 관계 정리, 상태 코드 정의, 이력 테이블 추가, 핵심 SQL 정리, API 분리 검토 순서로 제안되어야 한다.

## 데모에서 설명할 포인트

- `OrderService.java`가 상태 판단, 결제 확인, 배송 상태 반영, 관리자 보정을 한 흐름에서 처리한다.
- `03_order_status_update.sql`은 상태 변경 사유와 이전 상태를 별도 이력으로 남기지 않는다.
- `01_order_search.sql`과 `05_delivery_pending.sql`은 비슷한 조인과 상태 조건을 반복한다.
- `schema.sql`에는 주문 상태 이력 테이블이 없어서 변경 근거 추적이 어렵다.

## 주의할 점

- 모든 이름과 데이터는 데모용 가상 정보다.
- 실제 실행 가능한 애플리케이션이 아니라 업로드 분석용 소스 묶음이다.
- 이 샘플의 목적은 자동 코드 전환이 아니라 현대화 판단 보고서 초안 생성 검증이다.
