# 레거시 주문관리 업무 개요

## 1. 업무 목적

본 시스템은 온라인 접수 주문의 조회, 결제 확인, 배송 상태 갱신, 관리자 보정을 처리하는 내부 주문관리 업무 시스템이다. 주문이 접수되면 운영 담당자는 결제 상태를 확인하고 배송팀은 출고 가능 주문을 조회해 배송 상태를 갱신한다.

현행 시스템은 오래전에 화면 중심으로 만들어졌고 이후 결제 연계와 배송 연계가 추가되면서 서비스 코드와 SQL이 여러 위치에 분산되었다.

## 2. 사용자 역할

- 주문 운영자: 주문 검색, 주문 상세 확인, 고객 문의 대응, 상태 보정 요청 등록
- 결제 확인 담당자: 결제 성공/실패/취소 내역 확인, 주문 상태와 결제 상태 불일치 점검
- 배송 담당자: 결제 완료 주문의 배송 준비, 송장 입력, 배송 완료 처리
- 운영 관리자: 예외 주문 상태 수기 보정, 지연 주문 현황 확인, 재처리 대상 판단

## 3. 주요 업무 흐름

1. 고객 주문이 `LEGACY_ORDER`와 `LEGACY_ORDER_ITEM`에 생성된다.
2. 결제 연계 결과가 `LEGACY_PAYMENT`에 저장된다.
3. 주문 운영자는 주문 조회 화면에서 기간, 상태, 고객명, 결제 상태 조건으로 주문을 검색한다.
4. 결제 확인 담당자는 결제 성공인데 주문 상태가 접수 상태로 남은 건을 확인한다.
5. 배송 담당자는 결제 완료 상태의 주문을 배송 준비로 전환하고 `LEGACY_DELIVERY`를 갱신한다.
6. 운영 관리자는 연계 실패나 고객 문의가 있는 경우 주문 상태를 수기로 보정한다.

## 4. 현재 문제

- 주문 상태 변경 기준이 화면, 서비스 코드, SQL 조건에 분산되어 있다.
- 주문 상태가 `ORDER_STATUS` 단일 컬럼으로만 관리되어 이전 상태와 변경 사유를 추적하기 어렵다.
- 결제 성공 후 주문 상태 갱신 실패, 배송 상태 갱신 실패에 대한 재처리 기준이 명확하지 않다.
- 주문 조회, 배송 대기 조회, 결제 확인 SQL이 유사한 조인을 반복한다.
- 관리자 수기 보정이 `ADMIN_MEMO`와 `LAST_MODIFIED_BY`에만 남아 감사 추적이 부족하다.
- 배치 처리와 화면 수기 처리가 같은 테이블과 같은 상태 코드를 직접 수정한다.

## 5. 현대화 검토 목적

현대화 검토의 목적은 주문 상태 흐름을 명확히 정의하고, 주문/결제/배송 연계 실패 시 재처리 기준을 마련하며, 상태 변경 이력을 남길 수 있는 구조를 준비하는 것이다.

우선 검토 범위는 전체 주문 시스템 재구축이 아니라 다음 항목의 실행 가능성을 판단하는 것이다.

- 주문 상태 코드와 전이 기준 정리
- 주문 상태 변경 이력 테이블 도입
- 중복 SQL 정리와 DAO 호출 관계 명확화
- 주문 상태 변경 API 분리 검토
- 배치 처리와 운영자 수기 보정 흐름 분리
