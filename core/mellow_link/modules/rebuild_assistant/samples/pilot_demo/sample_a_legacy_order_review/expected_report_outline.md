# 기대 보고서 개요

## 1. 1페이지 요약

현행 주문관리 시스템은 주문 상태 판단, 결제 확인, 배송 갱신, 관리자 보정이 서비스 코드와 SQL에 강하게 결합되어 있어 상태 이력 관리와 단계적 서비스 분리가 우선 필요하다.

## 2. 분석 범위와 입력 자료

- `business_overview.md`는 주문 조회, 결제 확인, 배송 상태 갱신, 관리자 수기 보정이 한 업무 흐름에 포함되어 있음을 설명한다.
- `schema.sql`은 고객, 주문, 주문 품목, 결제, 배송 테이블의 관계를 제시하지만 주문 상태 이력 테이블은 없다.
- `sql/`의 5개 SQL은 조건 검색, 집계, 상태 업데이트, 결제 점검, 배송 대기 조회를 포함한다.
- `code/`의 Java 흐름은 Controller, Service, Repository가 SQL 파일을 호출하는 구조를 보여준다.

## 3. 현행 구조/업무 흐름 요약

- 화면 요청은 `OrderController`에서 `OrderService`로 전달되고, 서비스는 상태 전이 판단과 예외 보정을 수행한다.
- `OrderRepository`는 SQL 파일 단위로 DB 접근을 수행하지만 SQL 내부에 화면 조건과 업무 판단 조건이 섞여 있다.
- 주문 상태는 `LEGACY_ORDER.ORDER_STATUS`에 현재값으로만 남고, 결제 상태는 `LEGACY_PAYMENT`, 배송 상태는 `LEGACY_DELIVERY`에 각각 보관된다.
- 결제 승인 이후 주문 상태 갱신, 배송 준비 전환, 배송 지연 조회가 같은 주문 상태 값을 서로 다른 기준으로 해석한다.

## 4. 핵심 문제

- 화면/서비스/SQL/테이블이 강하게 결합되어 변경 영향 범위를 추적하기 어렵다.
- 상태 변경 기준이 코드의 `isAllowedTransition`, SQL 조건, 관리자 수기 보정 흐름에 분산되어 있다.
- 상태 변경 이력이 없어 이전 상태, 변경 주체, 변경 사유, 자동/수기 처리 여부가 구조화되어 남지 않는다.
- 주문 조회와 배송 대기 조회에서 유사한 조인과 조건이 반복된다.
- 결제/배송 연계 실패 시 재처리 기준이 SQL 조회 결과와 운영자 판단에 의존한다.

## 5. 개선 선택지

- A안: 현행 유지 + 일부 SQL 정리
  - 중복 조인과 조건을 정리하고 조회 SQL의 파라미터 기준을 문서화한다.
  - 단기 비용은 낮지만 상태 이력 부재와 수기 보정 의존은 남는다.
- B안: 서비스 계층 분리 + 상태 이력 테이블 도입
  - 상태 전이 규칙을 서비스 계층에 모으고 주문 상태 변경 이력 테이블을 추가한다.
  - 배치, 화면, 관리자 보정을 동일한 상태 변경 API 내부 규칙으로 통제할 기반을 만든다.
- C안: 주문 상태 API 분리 + 이벤트/배치 재설계
  - 주문 상태 변경을 별도 API로 분리하고 결제/배송 연계를 이벤트 또는 명확한 배치 재처리 기준으로 재구성한다.
  - 효과는 크지만 현행 업무 영향 분석과 단계 전환 계획이 필요하다.

## 6. 권장안

B안을 우선 추진하고, 상태 코드와 이력 구조가 안정된 뒤 C안을 단계적으로 검토하는 것이 적절하다. 즉시 전면 전환하기보다는 상태 기준 정리와 핵심 SQL 정리를 먼저 수행해 주문/결제/배송 불일치 리스크를 낮춰야 한다.

## 7. 리스크와 검토 필요 사항

- 무리한 전면 전환 시 주문 상태와 결제/배송 상태 불일치가 발생할 수 있다.
- 기존 관리자 수기 보정 데이터가 자유 문장으로 남아 있어 이력 전환 기준을 정의해야 한다.
- 결제 승인, 배송 준비, 배송 완료의 기준 시점과 책임 시스템을 명확히 해야 한다.
- 기존 화면에서 기대하는 검색 조건과 운영자 예외 처리 흐름을 누락하면 업무 저항이 생길 수 있다.
- 이력 테이블 추가 시 기존 주문 데이터의 초기 이력 적재 범위를 정해야 한다.

## 8. 단계별 실행 준비 계획

1. 테이블 관계와 주문/결제/배송 상태 코드 사용 위치를 목록화한다.
2. 주문 상태 전이 기준과 예외 보정 기준을 표준 상태표로 정의한다.
3. 주문 상태 이력 테이블 초안을 설계하고 변경 주체, 변경 사유, 처리 경로 컬럼을 정의한다.
4. `01_order_search.sql`, `04_payment_check.sql`, `05_delivery_pending.sql`의 중복 조인과 조건을 정리한다.
5. `OrderService`의 상태 변경 로직과 관리자 보정 로직을 분리한다.
6. 주문 상태 변경 API 분리와 배치 재처리 기준을 검토한다.

## 9. 분석 근거와 provenance

- 현행 결합도 근거: `code/OrderService.java`, `code/OrderRepository.java`
- 상태 이력 부재 근거: `schema.sql`의 `LEGACY_ORDER` 현재 상태 컬럼과 이력 테이블 부재 설명
- 중복 SQL 근거: `sql/01_order_search.sql`, `sql/05_delivery_pending.sql`
- 결제/주문 상태 불일치 근거: `sql/04_payment_check.sql`
- 수기 보정 의존 근거: `business_overview.md`, `code/OrderService.java`의 `manualStatusAdjust`
